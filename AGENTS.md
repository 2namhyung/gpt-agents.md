# Shared Codex Work Policy

Complete authorized work according to the user's goal and completion criteria. Prefer `rg` and narrowly scoped reads; use `rtk` only for large tests, builds, logs, or diffs. Read only relevant skills and documentation.

1. At product-work start, resume, or branch switch, confirm the chosen root, task branch, HEAD, and uncommitted changes. Confirm the official entry point and output path when relevant to the change. Skip Git details when the project does not use Git. Keep the baseline in one existing document, configuration, or task message; do not repeat it for every tool call. Do not assume an old worktree or commit is the current baseline.
2. Implement and verify from the chosen root through its official paths. Do not add product copies, alternate implementations, or bypass servers for test convenience. Use fixtures, temporary databases, caches, and build output in their designated locations. If an isolated worktree is needed, treat it as the root for that task, identify the handoff or merge target, and do not leave a duplicate final product.
3. Reduce failures to a minimal reproducer and expected versus actual behavior; trace from the official entry point. Fix shared business rules in the common path and convert representation differences at boundaries. Tests should call the same business code. Keep required error handling, security checks, and supported compatibility; do not add unsubstantiated future exceptions or extension frameworks.
4. Remove replaced implementations and unnecessary bypasses. If a staged migration, observation period, or follow-up deployment is needed, record an owner, completion criteria, removal target, and timing in the existing task record. Do not bulk-delete files outside the task scope.
5. Verify changed behavior, directly affected paths, and repository-required checks applicable to the change. Stop when they pass unless new failures, changes, or uncertainty remain. Reuse an existing cache only when its tool guarantees the relevant inputs, commands, and environment are identical. Do not treat a flaky pass as proof of a fix. Do not require new verification systems, full hashes on every turn, or new documentation by default.
6. If two fixes for the same cause fail, stop patching and reassess the baseline, reproducer, and hypothesis. Hand off to a suitable role when needed; do not repeatedly escalate models for environment or permission issues. Clean up only your own failed changes; never revert someone else's work.
7. Handle small investigations and edits directly. Delegate independent research, long runs, or clearly bounded implementation when useful, without duplicating the work. Use the delegation message itself as a concise task card covering goal, paths, ownership, completion criteria, checks, and needed contracts; create a separate document only for structural changes that need one. Follow model and reasoning settings in role TOMLs. Children must not delegate. Keep one writer per shared checkout, including documentation, and parallelize independent reads only.
8. Require independent review for changes to authentication, authorization, schemas, deployments, or behavior spanning multiple modules. Use a separate execution verifier only for long runs or additional independent evidence; reviewers do not edit product files. Briefly report the final root, baseline, run instructions, changes, checks, and unknowns. Do not claim improvement rates before measuring them.

Role instructions and writer rules do not provide OS-level permission isolation. Child agents inherit the parent session's permissions.
